# 13 · 座位位图库存设计

## 目标

分段库存只回答“每个相邻车段还剩几张票”，无法保证同一乘客从出发站到终点站始终坐在同一个座位。
本设计在原有分段库存上增加具体座位位图，解决以下问题：

- 同一张票必须全程使用同一个座位
- 各车段都余票充足时，仍可能因座位集合不重叠而没有连续余票
- 高并发下不能把同一个座位同时卖给两张区间重叠的票
- 退票和部分退票必须只释放对应乘客的座位

## 存储模型

`ticket_stock` 仍是每行对应：

```text
travel_date + train_id + segment_index + seat_type
```

新增：

```sql
sold_seat_mask VARBINARY(160)
```

位图中的第 0 位对应座位编号 1，第 99 位对应座位编号 100。
使用二进制存储而不为每个车段插入 600 条座位记录，可以显著减少固定数据量。

`ticket_order_item` 新增：

```sql
seat_index INT
```

它与位图位号对应。`coach_no` 和 `seat_no` 继续保存面向用户的座位信息。

## 连续余票计算

对于一个车次的第 3 到第 7 段：

```text
unionSold = soldMask(3)
          | soldMask(4)
          | soldMask(5)
          | soldMask(6)
          | soldMask(7)

available = fullMask & ~unionSold
remaining = bitCount(available)
```

这等价于：

```text
available = freeMask(3)
          & freeMask(4)
          & freeMask(5)
          & freeMask(6)
          & freeMask(7)
```

但先合并已售位图、再求一次补集，比逐段求交集更直接。

`MIN(remaining_count)` 仍然可以作为监控指标，但不能作为对号入座票的最终余票结果。

## 下单

下单事务会锁定覆盖区间的全部库存行：

```sql
SELECT ...
FROM ticket_stock
WHERE travel_date = ?
  AND train_id = ?
  AND seat_type = ?
  AND segment_index BETWEEN ? AND ?
ORDER BY segment_index
FOR UPDATE;
```

在锁内重新计算连续可用座位，选择乘客数量对应的座位位图，再把同一组座位位写入全部覆盖车段。

这样并发请求会串行通过库存行锁，后到的事务会读取前一个事务提交后的位图，不会重复选中同一座位。

## 取消、超时和退票

订单明细保存 `seat_index`。取消或退票时：

```text
releasedMask = 该订单明细中的 seat_index 对应位
newSoldMask = oldSoldMask & ~releasedMask
sold_count = bitCount(newSoldMask)
remaining_count = total_count - sold_count
```

所有覆盖车段都完成更新后，订单状态才能提交。

## Redis 的职责

第一阶段：

- MySQL 位图是座位占用的最终事实
- Redis 数字库存只承担异步下单前的快速容量准入
- MySQL 事务锁和位图更新负责最终占座

因此 Redis 准入通过后，数据库仍可能因为“没有连续同座”而拒绝订单。
异步消费者必须按失败补偿流程释放 Redis 预扣。

## 测试重点

- 两段分别有空座但没有共同空座时，连续余票必须为 0
- 同一订单的所有覆盖车段使用完全相同的座位位图
- 并发抢最后一张票只能有一个订单成功
- 取消和退票只释放订单对应座位
- 部分退票不影响其他乘客
- 旧数据没有位图时，通过 `sold_count` 和 `remaining_count` 兼容生成确定性初始位图
