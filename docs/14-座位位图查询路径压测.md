# 14 · 座位位图查询路径压测

## 测试目的

比较本地车段车次哈希索引和 Redis 查票对象分别对查询性能的贡献，并测试清空 Redis 后的冷缓存预热效率。

## 测试环境

- 后端：Spring Boot 4.1.1，Java 17
- 数据库：MySQL，110 个车站、1,000 个车次、284,400 条库存
- Redis：cache 组 1 Master + 2 Replica，stock 组 1 Master + 2 Replica
- 压测场景：北京南到上海虹桥，2026-11-26，二等座，第一页
- 压测并发：64
- 每组持续：20 秒
- 压测工具：`scripts/max_load_test.py`

所有场景使用相同数据库、Redis、JVM、连接池和查询参数。每组测试前清理对应缓存，避免上一组污染下一组。

## 四组 QPS

| 场景 | Redis 查票对象 | 本地哈希索引 | QPS | P50 | P95 | P99 | 失败数 |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| 无索引、无 Redis | 否 | 否 | 2,070.66 | 28.11ms | 54.99ms | 78.18ms | 0 |
| 无索引、有 Redis | 是 | 否 | 8,714.24 | 2.42ms | 10.45ms | 18.78ms | 0 |
| 有索引、无 Redis | 否 | 是 | 3,459.03 | 16.75ms | 34.50ms | 50.33ms | 0 |
| 有索引、有 Redis | 是 | 是 | 8,633.55 | 2.42ms | 10.68ms | 19.43ms | 0 |

## 结论

### 1. 索引在没有 Redis 时提升明显

```text
2,070.66 QPS → 3,459.03 QPS
提升约 67.05%
```

同时：

```text
P99：78.18ms → 50.33ms
降低约 35.62%
```

原因是慢查询需要执行三次数据库查询，而索引路径只需要通过 HashMap 找到车段，再执行一次座位位图批量查询。

### 2. Redis 命中时索引影响几乎消失

```text
无索引、有 Redis：8,714.24 QPS
有索引、有 Redis：8,633.55 QPS
```

差约 `0.93%`，属于单次压测波动。Redis 查票对象已经直接返回完整页结果，不再访问本地索引或数据库，因此热缓存路径不会因为索引开关产生明显变化。

### 3. Redis 对有索引路径提升最大

```text
有索引、无 Redis：3,459.03 QPS
有索引、有 Redis：8,633.55 QPS
提升约 149.59%
```

这说明索引解决的是 Redis 未命中后的数据库回源效率，而 Redis 解决的是重复热点查询不访问后端数据库的问题。

### 4. 完整链路相对慢查询

```text
2,070.66 QPS → 8,633.55 QPS
提升约 316.95%

P99：78.18ms → 19.43ms
降低约 75.15%
```

## 索引对 Redis 冷缓存预热的影响

Redis 服务本身的启动时间与业务索引无关。这里测试的是应用启动后，清空 cache Redis，再生成 240 个热门查票对象所需的时间。

| 场景 | 预热对象数 | 预热耗时 |
| --- | ---: | ---: |
| 无索引 | 240 | 2,675ms |
| 有索引 | 240 | 1,517ms |

有索引时预热耗时降低：

```text
(2,675 - 1,517) / 2,675 = 43.29%
```

速度约为无索引时的：

```text
2,675 / 1,517 = 1.76 倍
```

索引减少了每个缓存对象首次生成时的三阶段数据库查询，因此可以更快完成 Redis 冷启动预热。

## 真实混合流量复测

单一热点站对不能代表实际客流，因此又增加了一组 60 秒混合查询。

查询池来自实际 `train_segment` 数据，共 186 个有效有向站对：

```text
70%：20 个高频站对
20%：100 个中频站对
8%：66 个冷门站对
2%：不存在的站对
```

同时随机选择 3 天日期、商务座/一等座/二等座和 1-3 页，64 并发持续 60 秒。

### 混合流量 QPS

| 场景 | QPS | P95 | P99 | 缓存命中率 | 索引查询 | MySQL 回源 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 无索引、无 Redis | 2,202.32 | 49.11ms | 64.67ms | 0% | 0 | 132,226 |
| 有索引、无 Redis | 1,516.37 | 67.88ms | 86.37ms | 0% | 89,243 | 0 |
| 无索引、有 Redis | 7,265.00 | 10.67ms | 20.37ms | 95.75% | 0 | 18,550 |
| 有索引、有 Redis | 7,552.07 | 10.24ms | 21.74ms | 94.10% | 17,621 | 0 |

另外重复一轮无缓存测试：

```text
无索引、无 Redis：2,272.34 QPS，P99 56.62ms
有索引、无 Redis：1,545.53 QPS，P99 84.65ms
```

### 新发现

当前索引快路径在混合流量、关闭 Redis 时反而比 MySQL 慢查询慢约 31%。

原因是：

- `RouteBucket` 返回该站对全部候选车次。
- 当前实现先批量查询所有候选车次的库存位图。
- 然后再计算连续余票、过滤和分页。
- 高频站对可能有 30-50 个车次，实际只展示第一页 10 个车次。
- `findForSearch` 当前还会读取车次全部席别的库存行，而不只是请求席别。

慢查询路径则先分页出当前页车次，再只读取这 10 个车次的席别明细。因此在高车次数线路上，索引路径一次加载的数据反而更多。

### 结论修正

- 索引在单一热点、候选车次较少的查询中明显更快。
- 索引在 Redis 热缓存命中时影响很小，因为不会进入索引路径。
- 索引在真实宽线路混合查询中不一定更快，当前实现需要按席别过滤并分块处理候选车次。
- Redis 仍然是当前最明显的整体提升来源，特别是对高频重复查询。

### 下一步优化

1. `TicketStockMapper.findForSearch` 增加 `seat_type` 条件。
2. 索引查询按候选车次分块处理，不再一次加载全部车次。
3. 每块计算连续余票，累计到足以填满目标分页后停止。
4. 将每个车次的命中状态写入短 TTL 本地缓存或 Redis 读模型。
5. 优化后重新执行本混合查询池，验证索引在宽线路场景是否转为正收益。
