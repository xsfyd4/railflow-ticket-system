# 05 · 接口清单总览

> 整个项目要做哪些接口、每个接口干什么。共 45 个，按阶段排列。
> 路径前缀的含义：`/api/public` 不需要登录，`/api/user` 用户端，`/api/admin` 管理端。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/public/ping` | 服务存活探针，确认后端起来了 |
| GET | `/api/public/db-check` | 数据库连通探针，确认能读到 MySQL 数据 |

## 阶段 2 · 登录注册（6 个）

| 方法 | 路径 | 作用 | 要登录 |
| --- | --- | --- | --- |
| POST | `/api/user/auth/register` | 注册新账号，密码 BCrypt 加密入库 | 否 |
| POST | `/api/user/auth/login` | 登录，校验密码并签发 JWT | 否 |
| GET | `/api/user/auth/me` | 查当前登录人的信息（不含密码） | 是 |
| POST | `/api/user/auth/logout` | 退出登录（JWT 无状态，实质是前端丢 token） | 是 |
| POST | `/api/admin/auth/login` | 管理员登录，签发的 token 里 role=ADMIN | 否 |
| GET | `/api/admin/auth/me` | 查当前登录的管理员信息 | 是 |

## 阶段 3 · 基础数据管理（16 个）

这一阶段全在管理端，做的是"把车次数据录进去"。是纯增删改查，用来练分层和事务。

### 车站（6 个）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/admin/stations` | 分页查车站，支持按名称/拼音/城市搜索 |
| GET | `/api/admin/stations/{id}` | 查单个车站详情 |
| POST | `/api/admin/stations` | 新增车站 |
| PUT | `/api/admin/stations/{id}` | 修改车站 |
| DELETE | `/api/admin/stations/{id}` | 删除车站（被车次引用时禁止删除） |
| GET | `/api/public/stations` | 车站下拉列表，用户端查票页要用 |

### 车次（4 个）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/admin/trains` | 分页查车次，支持按车次号/类型筛选 |
| POST | `/api/admin/trains` | 新增车次（G1001 这种基本信息） |
| PUT | `/api/admin/trains/{id}` | 修改车次 |
| DELETE | `/api/admin/trains/{id}` | 删除车次（连带删除停站和分段） |

### 停站、分段、票价（6 个，★ 这一阶段的核心）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/admin/trains/{id}/stops` | 查某车次的停站列表（按顺序、带时刻） |
| PUT | `/api/admin/trains/{id}/stops` | **整体保存停站**——重排序号，并自动重建分段 |
| GET | `/api/admin/trains/{id}/segments` | 查某车次切分出来的所有段 |
| GET | `/api/admin/trains/{id}/prices` | 查每段每席别的票价 |
| PUT | `/api/admin/trains/{id}/prices` | 保存票价 |
| GET | `/api/public/trains/{id}/stops` | 车次经停站，给用户端"车次详情"用 |

> `PUT .../stops` 是这一阶段最值得琢磨的接口：
> 管理员在界面上拖动停站顺序、增删中间站，后端要重排 `stop_order`、
> 重新计算 `train_segment`，还要处理"已经有库存了还能不能改"这种问题。
> 它涉及事务和级联更新，是阶段 3 最像"真实项目"的地方。

## 阶段 4 · 库存与余票（5 个）

这一阶段是整个项目的技术核心。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/admin/stocks/generate` | 为未来 N 天批量生成库存（每段每天每席别一条） |
| GET | `/api/admin/stocks` | 查某天某车次的逐段余票，看得见每段还剩几张 |
| PUT | `/api/admin/stocks/{id}` | 手工调整某段余票（比如临时加挂车厢） |
| GET | `/api/user/tickets/search` | **查票**：出发站 + 到达站 + 日期 → 车次列表，含各席别余票和票价 |
| GET | `/api/user/tickets/{trainId}` | 车次详情：经停站、各席别的余票与价格 |

> 查票接口是用户端的第一屏，也是性能最关键的地方。
> 它要一次查出十几个车次、每个车次算区间最小值、还要算总价——
> 阶段 4 会把那条聚合 SQL 反复打磨。

---

## 阶段 5 · 订单与乘车人（10 个）

这一阶段的核心是**事务和并发**：怎么保证两个人同时抢最后一张票时不超卖。

### 乘车人（4 个）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/user/passengers` | 常用乘车人列表 |
| POST | `/api/user/passengers` | 新增乘车人（姓名 + 证件号） |
| PUT | `/api/user/passengers/{id}` | 修改乘车人 |
| DELETE | `/api/user/passengers/{id}` | 删除乘车人 |

### 订单（6 个）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/user/orders` | **提交订单**：校验余票 + 扣减各段库存 + 落订单，全在一个事务里 |
| POST | `/api/user/orders/{orderNo}/pay` | 模拟支付，把订单从"待支付"改成"已出票" |
| POST | `/api/user/orders/{orderNo}/cancel` | 取消订单，按 `order_segment` 回补库存 |
| POST | `/api/user/orders/{orderNo}/refund` | 退票，回补库存并记录 |
| GET | `/api/user/orders` | 我的订单列表（可按状态筛选） |
| GET | `/api/user/orders/{orderNo}` | 订单详情（含每个乘车人的票） |
