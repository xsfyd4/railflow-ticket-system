### 12. 2026-10-23：完成支付超时自动取消

**做了什么**

- 开启 Spring `@Scheduled`。
- 每分钟扫描最多 100 个到期待支付订单。
- 每个订单使用独立事务处理。
- 处理前通过 `FOR UPDATE` 重新锁定订单。
- 再次确认订单仍为待支付且确实已过期。
- 回补订单覆盖的全部库存。
- 修改订单为已取消并记录 `cancelled_at`。
- 增加 `(status, expire_time)` 索引，避免扫描过期订单时扫整张订单表。
- 单个订单失败只记录日志，不影响同批其他订单。

**解决的问题**

- 用户下单后不支付时，库存不会永久占用。
- 支付、用户取消、定时任务并发操作同一订单时，行锁保证状态串行变化。
- 过期任务重复扫描不会重复回补库存。
- 已支付或未过期订单不会被误取消。

**验证**

- 过期订单自动取消并回补库存。
- 同一过期订单再次处理时不会重复回补。
- 未过期订单和已支付订单不会被取消。

### 14. 2026-10-24：新增支付流水表，支付幂等兜底

**做了什么**

- 新增 `pay_log` 表（第 13 张表），记录每一次支付尝试。
- 三个数据库唯一约束兜底：
  - `uk_pay_request(request_id)`：同一个幂等键只能生成一条流水；
  - `uk_pay_external(external_txn_id)`：第三方支付流水号只能入账一次；
  - `uk_pay_success_order(success_order_id)`：生成列 + 唯一索引，保证一个订单最多一条成功流水。
- `POST /api/user/orders/{orderNo}/pay` 支持 `Idempotency-Key` 请求头或 body `requestId`；
  都不传时按“用户 + 订单”生成固定键，重复点击同样只扣一次。
- 支付拆成两个事务边界：
  - `openAttempt` 用 `REQUIRES_NEW` 独立事务插入“处理中”流水，抢占幂等键；
  - `complete` 事务内锁订单、条件更新为已支付，并把流水置为成功。
- 重复支付不再抛“订单状态错误”，而是返回首次成功的 `payNo`，并标记 `idempotentReplay=true`。
- 并发不同幂等键支付：后到的流水置为“已关闭”，不会二次扣款。
- 超时 / 取消后支付：拒绝，并留下失败流水，便于对账。
- 新增 `GET /api/user/orders/{orderNo}/payments` 查询全部支付尝试。
- 新增增量迁移脚本 `sql/04-pay-log.sql`。

**解决的问题**

- 支付接口不幂等：重复点击或网络重试会返回失败，用户以为没付成功。
- 订单表没有支付记录，无法回答“这笔钱扣没扣、扣了几次”。
- 并发支付缺少数据库级“一单最多一条成功流水”的兜底。
- 第三方异步回调重复到达没有去重依据（已预留 `external_txn_id` 唯一索引）。

**验证**

- 全量 27 个测试通过（原 19 个 + 新增 8 个支付幂等用例）。
- 同一幂等键重复支付返回同一个 `payNo`，`pay_log` 只有 1 条记录。
- 不同幂等键重复支付：1 条成功 + 1 条已关闭，订单只支付一次。
- 同键并发 / 不同键并发：成功流水都只有 1 条。
- 超时、取消后支付均被拒绝，并留下 `status=2` 的失败流水。
- 幂等键跨订单复用被拒绝（错误码 2010）。

**仍未解决**

- 当前只有 `MOCK` 模拟渠道，真实第三方支付与异步回调尚未接入。
- 支付流水暂时没有 T+1 对账任务（与渠道流水逐笔核对）。

### 15. 2026-10-24：建立无 Redis 的 HTTP 压测基线

**做了什么**

- 新增可重复执行的 HTTP 压测脚本 `scripts/load_test.py`。
- 对查票接口执行 1、8、16、32、64 并发测试。
- 记录 QPS、平均延迟、P50、P95、P99、最大延迟和失败请求数。
- 增加 16 个账号同时抢最后一张票的集成测试。
- 将测试环境、原始 JSON、瓶颈分析和复现命令整理为压测报告。

**结果**

- 8 并发约 1531 QPS。
- 16 并发约 2534 QPS，P95 约 10ms。
- 32/64 并发 QPS 基本维持在约 2.5k，但 P95 增加。
- 所有 HTTP 压测请求成功，没有超卖或库存重复回补。

**发现**

- 当前 16 并发已经接近本机吞吐平台。
- 64 并发线程栈采样中，65 个 HTTP 工作线程有 51 个停在 Hikari 获取连接，
  另外 10 个正在等待 MySQL 返回。
- 当前首要瓶颈已确认是 HikariCP 10 个连接形成的排队，三次 SQL、Debug 日志和同机部署会放大影响。
- 64 并发时 Java 约占整机 26.15% CPU、MySQL 约占 10.57%，合计约 36.72%，
  说明 CPU 尚未跑满；IDEA 启动参数 `-XX:TieredStopAtLevel=1` 也限制了 JIT 性能。
- 该数据作为接入 Redis 前的对照基线。

**下一步**

- 接入 Redis 查票缓存后重复同一套压测。
- 对比 QPS 和 P95，而不是只记录单次最高 QPS。

### 16. 2026-10-24：建立独立日志体系并调整连接池

**做了什么**

- 新增 `docs/logs/`，分别维护代码、数据库、Redis 和 MQ 四类工作日志。
- 新增 `logback-spring.xml`，运行日志拆分为：

- HikariCP 最大连接从 10 调整为 20，最小空闲从 2 调整为 5。
- 新增数据库访问层和 Spring MVC 进程内连接池对照基准。

**验证**

- 数据库访问层池 10 → 池 20：
  - QPS 从 9201.52 提升至 15557.34，约 +69%。
  - P95 从 42.41ms 降至 20.97ms。
- Spring MVC 进程内池 10 → 池 20：
  - QPS 从 1716.59 提升至 3102.65，约 +81%。
  - P50 从 36.17ms 降至 17.64ms。
- 池 20 时把请求线程从 64 增加到 128：
  - QPS 从 3102.65 降至 2477.24。
  - P95 从 47.64ms 升至 80.30ms。
- 结果证明连接池是当前可调瓶颈之一。

**只读事务实验**

- 三轮交替基准中，稳定阶段无事务约 5.9k QPS，只读事务约 5.5k QPS。
- 只读事务中位延迟更低，但会长期占用连接，整体吞吐略低。
- 因为下一步接 Redis，缓存命中不应获取数据库连接，最终撤回查票外层事务。
- 后续只在 Redis 未命中的独立数据库回源 Service 中评估短事务。

**仍未完成**

- 当前 8080 实例仍是旧配置，需重启后再跑真实 HTTP 64 并发。
- 扩容连接池后要继续观察 MySQL CPU、锁等待和连接上限。

### 17. 2026-10-24：接入 Redis 查票缓存

**做了什么**

## 20. 2026-10-26：修复新增车次流程不完整缺陷

**问题**

管理端当前“新增车次”只创建 `train` 主记录，只填写车次号和始发站、终到站。
创建后不会同时生成：

- `train_stop`
- `train_segment`
- `train_segment_price`
- `ticket_stock`

因此新车虽然默认显示为“运行中”，但用户查不到、无法下单，也不能生成库存。

**根因**

- `TrainSaveDTO` 按设计只承载车次基本信息。
- `TrainServiceImpl.create()` 只执行 `INSERT train`。
- 停站和票价仍需要调用独立的 `PUT /api/admin/trains/{id}/stops` 和
  `PUT /api/admin/trains/{id}/prices`。
- 当前管理端车次页面只实现“查看线路”，没有停站编辑和票价编辑入口。
- 新车默认 `status=1`，在尚未配置完整时会造成“启用但不可售”的误导状态。

**影响**

- 管理端新增车次属于半成品流程。
- 用户端不会查询到该车次。
- 库存生成会跳过没有分段的车次。
- 只能通过直接调用停站和票价 API 完成后续配置。

**修复内容**

1. 新增管理端三步向导：基本信息 → 停站时刻 → 分段票价。
2. 新增 `POST /api/admin/trains/full` 事务型完整创建接口。
3. 始发站、终到站和总里程由停站首尾自动推导。
4. 每一段必须配置商务座、一等座和二等座价格，否则整个创建事务回滚。
5. 车次列表的“线路”弹窗增加停站编辑和票价编辑。
6. 有停站时，普通车次编辑不能修改始发站、终到站或总里程。
7. 有订单时禁止清空库存和修改停站。
8. 有库存但无订单时，提供“清空该车次库存”入口，清空后允许重配停站。
9. Redis 中该车次全部日期的数字库存 Key 会通过 `SCAN` 分批清理。

**关联缺陷修复**

`TrainServiceImpl.page()` 的分页 offset 原来写死为：

```java
int offest = (page - 1) * 10;
```

已改为：

```java
int offset = (page - 1) * size;
```

**状态**

已修复。

**验证结果**

- `TrainFullCreateIntegrationTest` 4 个场景全部通过。
- 完整创建车次后自动生成 3 个停站、2 个分段、6 条票价。

### 21.6 重要的长期架构结论

- 项目长期定位是高并发、大数据量；
- 当前 100 车次只是功能验证数据，不能据此否定扩展性设计；
- MySQL 始终是订单和最终库存事实来源；
- Redis 和 MQ 不承担最终交易事实；
- 查票读模型与下单库存模型职责不同；
- 高并发方向应物理拆分：
  - `redis-cache` 保存查票结果，允许淘汰、可降级 MySQL；
  - `redis-stock` 保存下单预扣，禁止淘汰、要求重点监控；
- 只拆逻辑库号不能隔离 CPU、内存、网络和故障域；
- 静态路线与票价适合 Caffeine；
- 动态库存适合 Redis 读模型和原子预扣；
- 全量库存组合预计算不是首选，优先保存原始分段库存；
- 需要周期性更新时使用版本化快照或增量同步，不能直接覆盖运行中的预扣 Key。

### 22. 2026-10-27～28：Redis 高可用、读模型、UUID 幂等与对账

**做了什么**

- 建立 1 Master、2 Replica、3 Sentinel 的开发环境。
- 库存、版本号和 UUID 只写 Master；查票快照轮询两个 Replica。
- 查票结果改为单对象平行数组，一次 `GET` 返回整页。
- 订单、异步下单和支付接入 Redis UUID 快状态，保存请求摘要和 ownerToken。
- 增加库存预热、热门查票对象预热、MySQL/Redis 分批对账。
- 对账使用日期+车次短租约，预扣 Lua 会识别租约并暂缓。
- 保留 MySQL 同步查票和同步下单的完整降级路径。

**解决的主要问题**

- Windows/JDK 23 下 Lettuce/NIO 不可用，主写恢复为 Jedis。
- Sentinel 用容器名监控 Master 会在容器停止后失去 DNS，已改为固定 IP。
- Sentinel 只读绑定配置无法持久化选举结果，已改为可写命名卷。
- 固定幂等键在数据库清理后残留旧 `SUCCESS`，现在数据库无结果时可安全回收。
- 预热/对账增加跨轮游标，避免每轮都只扫描前 5000 行。

**验证结果**

- 完整后端测试 57 个：53 通过，4 个跳过，0 失败。
- 用户端、管理端生产构建成功。
- 真实 HTTP 登录和查票成功。
- 一个 Replica 下线后查票仍成功。
- Master 下线后 Sentinel 自动选主，后端自动跟随；原 Master 恢复后重新作为 Replica 加入。
- Redis 全停时，查票和同步下单自动化测试均通过。
