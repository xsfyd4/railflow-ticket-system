# 11 · 项目优化想法清单

> 这份文件是项目的长期设计备忘。以后讨论出值得保留的想法，都追加到这里。
> 状态：✅ 已完成；🔜 建议下一步；🧪 先压测/测量；⏸ 暂缓；❌ 已评估但不采用。

## 零、项目长期定位

以下是后续设计和评审默认采用的长期约束：

- 项目目标是**高并发、大数据量**的铁路购票系统，对标方向接近真实 12306，而不是只完成低流量课程演示。
- 当前 1000 个车次、110 个车站和 284400 条库存用于扩大规模验证，**仍不能把当前数据量下的性能结论当成最终架构结论**。
- 所有新设计都要考虑高峰期查询、库存争抢、连接池、Redis 热点、RabbitMQ 积压和数据库写入上限。
- MySQL 仍是订单和最终库存的事实来源；Redis 和 RabbitMQ 负责缓存、准入、排队和削峰，不能替代交易事务。
- 静态路线和票价优先考虑本地 Caffeine/版本化读模型；动态库存需要独立的 Redis 读写模型。
- 高并发下建议拆分物理 Redis：`redis-cache` 只存查票结果，`redis-stock` 只存下单预扣库存，分别设置淘汰、持久化和故障策略；只拆逻辑库不算资源隔离。
- 任何缓存、索引、异步和读模型优化都必须通过真实压测、执行计划和故障演练验证。
- 设计优先关注可恢复性、幂等、对账、限流、监控和数据归档，而不是只追求单次接口能跑通。

这条定位是长期约束，后续出现新的有效设计思路时继续记录在本文件。

## 一、产品与项目结构

- ✅ 采用用户端、管理端、后端三端结构，用户端和管理端都必须登录。
- ✅ 用户端负责查票、下单、支付、退票和购买记录；管理端负责基础数据、库存和后续系统统计。
- ✅ 按功能分包，而不是所有 Controller、Service 平铺在根目录。
- ✅ DTO、Entity、VO 分离：DTO 接请求，Entity 对应数据库，VO 返回前端。
- ✅ 前后端都做参数校验；后端校验才是最终安全边界。
- ✅ 用户端 Vue 已覆盖登录注册、查票、乘车人、同步下单、订单和退改签。
- ✅ 管理端 Vue 已覆盖登录、概览、车站、车次、线路详情和库存管理。
- ✅ 新增车次使用基本信息、停站时刻、分段票价三步向导，并在一个后端事务中落库。
- ✅ 车次已有库存时禁止直接改停站，无订单时可清库存后重配。
- ✅ 车次已有订单时禁止清库存和修改线路结构。
- 🔜 管理端补全部订单查询、详情、代客退票和经营统计。

## 二、车票与数据库模型

- ✅ 车次按停站顺序 `stop_order` 管理，绝不按自增 id 推导运行方向。
- ✅ 相邻两站组成一个 `train_segment`；查询任意两站时转换为连续分段区间。
- ✅ 余票按“日期 + 车次 + 段 + 席别”存储，区间余票取所有覆盖段的最小值。
- ✅ 区间票价取所有覆盖段价格之和，前端不传金额。
- ✅ 订单不按“每位乘客 × 每一段”展开，避免 `order_segment` 数据膨胀。
- ✅ 订单主表保存统一起止段区间，订单明细一位乘客一行，并保存姓名、证件号、价格快照。
- ✅ 取消、退票按订单保存的段区间统一回补库存。
- ✅ 索引遵循“等值字段在前、范围字段在后”。
- ✅ 新增票价查询索引 `idx_price_query(train_id, seat_type, segment_index)`。
- ⏸ 当前没有数据库物理外键，关系由应用层维护；上线前重新评估完整性和运维代价。
- 🔜 如果支持每位乘客不同目的地，再把区间移动到订单明细或新增区间表。
- 🔜 引入车次运行图版本表，后续支持同一车次号在不同日期使用不同停站方案。

## 三、下单与并发一致性

- ✅ 同步下单和正式订单创建使用 MySQL 事务。
- ✅ 覆盖多个分段时用一条范围 UPDATE 扣库存，影响行数必须等于分段数。
- ✅ `remaining_count >= count` 与减法由 MySQL 原子执行，防止超卖。
- ✅ 事务中途异常会回滚已经部分扣减的库存。
- ✅ 下单不信任前端价格、段号和用户 id；全部由后端查询并计算。
- ✅ 同一乘车人不能在同一订单重复出现。
- ✅ 订单状态变更使用行锁和条件更新，取消、支付、退票不会重复执行。
- ✅ 订单创建 SQL 已优化：乘车人批量查询、订单明细批量插入。
- 🔜 后续若仍以数据库为中心，可把车段和票价合并为一次只读查询，但要保留清晰的错误分类。
- ❌ 不把 Redis 预扣和 RabbitMQ 发布塞进 MySQL 事务，避免远程系统故障拖垮数据库事务。

## 四、支付、订单与幂等

- ✅ 支付使用 `pay_log` 流水和唯一幂等键，重复支付只成功一次。
- ✅ 一个订单最多一条成功支付流水。
- ✅ 支付、取消、退票、超时取消都有状态校验。
- ✅ 支持部分退票和全部退票。
- ✅ 异步下单使用客户端 `Idempotency-Key`，网络重试不生成第二笔订单。
- ✅ 支付、退票等关键动作保留操作记录和失败原因。
- ✅ 幂等请求保存完整请求摘要，包含排序后的 passengerIds，避免同 Key、同人数但不同乘车人被错误重放。
- ✅ 前端把 pending 下单/支付的 Idempotency-Key 持久化到 sessionStorage，直到明确终态，避免刷新后生成新 Key。
- ✅ Redis 幂等快状态层：`SET NX/Lua PROCESSING + requestHash + ownerToken + TTL`，SUCCESS 缓存结果，Redis 未命中再查 MySQL；MySQL 唯一键继续兜底。
- ⏸ Redis 只作为快状态层，不能替代 `ticket_order`、`order_request`、`pay_log` 的唯一约束。
- 🔜 接入真实支付时增加异步回调和外部流水号幂等。
- 🔜 支付、退款可以通过 MQ 发布领域事件，但数据库状态仍是事实来源。

## 五、Redis 与缓存

- ✅ 查票使用 Cache Aside：完整 `PageResult<TicketVO>` 写 Redis，基础 TTL 10 秒并增加 ±20% 随机抖动。
- ✅ 空结果使用约 3 秒短 TTL；索引 READY 时不存在站对直接返回，不访问 Redis/MySQL。
- ✅ 热点缓存未命中使用 Redis 重建锁，等待者按指数退避复用回填结果。
- ✅ 冷缓存 64 并发热点只触发 1 次 HTTP 查票 SQL；热缓存 128 并发约 13.6k QPS。
- ✅ 缓存版本包含全局版本和日期版本，基础数据或库存变化后递增版本。
- ✅ 事务提交后才失效缓存，避免数据库回滚但缓存先被删除。
- ✅ Redis 查票异常时降级 MySQL。
- ✅ 分段数字库存使用 `ticket:stock:{date:trainId}:seat:segment`。
- ✅ Redis Cluster 使用 Hash Tag，保证同一车次同一天多分段可执行一段 Lua。
- ✅ Lua 先检查全部段，再统一预扣，避免半扣。
- ✅ 取消、退票、超时和消费失败回补 Redis。
- ✅ 管理员调整库存后从 MySQL 重新覆盖 Redis。
- ✅ 增加定时 Redis/MySQL 分批对账任务。
- ✅ 把车段车次和票价静态索引放入后端本地内存。
- ✅ 静态索引采用状态机和版本重建，避免管理员改价后继续使用旧数据。
- ❌ 单独增加 Caffeine 价格缓存：静态车段索引已经包含全部票价，重复缓存没有收益。
- ✅ 物理拆分 `redis-cache` 与 `redis-stock`，各自 1 Master + 2 Replica + 3 Sentinel。
- ⏸ 0.5 秒覆盖运行中库存 Key 和全路线组合预计算暂不采用；需要时使用版本化快照或增量同步。
- ❌ 不用 `KEYS` 扫描删除业务缓存；使用版本号或明确的 Key 集合。

## 五-A、Redis 高可用与读模型（本次落地）

- ✅ cache 与 stock 各使用 `1 Master + 2 Replica + 3 Sentinel`：两个 Master 分别承接查票和交易写操作，cache Replica 分担查票对象读取。
- ✅ 开发环境使用固定节点 IP，避免 Master 容器停止后 Docker DNS 消失导致 Sentinel 进入 `tilt`；Sentinel 配置写入命名数据卷，可持久化选举结果。
- ✅ 查票对象优先从 Replica 轮询读取；Replica 缺失或故障时尝试另一个副本并回退 Master/MySQL，库存和 UUID 决策禁止从 Replica 读。
- ✅ 热点查票使用“单对象 + 平行数组”快照：一次 `GET` 拿到整页，数组同一小标对应同一车次，避免 N 次细粒度 Redis 往返。
- ✅ UUID 幂等状态使用 `SET NX`/Lua 原子抢占，保存用户、请求摘要、ownerToken、状态和结果号；Redis 是快闸门，MySQL 唯一键是最终兜底。
- ✅ 启动后预热未来库存和热门站对查票快照；库存预热只用 `SET NX`，不覆盖正在发生的预扣，并用跨轮游标扫描超过单轮上限的数据。
- ✅ 定时执行 MySQL/Redis 库存对账；存在活跃异步预扣时跳过该日期车次，不能盲目覆盖；修复时使用短租约，预扣 Lua 会识别租约并暂缓。
- ✅ 同步查票和同步下单的完整 MySQL 路径永久保留，作为 Redis 全停或主从切换期间的降级通道。
- ✅ 已验证一个 Replica 下线后仍可查票，Master 下线后 Sentinel 自动选主，原 Master 恢复后重新以 Replica 加入。
- ✅ 两个物理 Redis 数据组已经落地；全国规模继续增长后再为单组引入 Redis Cluster 分片。

### 本机压测结论

- ✅ 旧 MySQL 版本约 2.5k QPS；当前 Redis 热点查票短时峰值约 **12.8k QPS**，60 秒稳定约 **11.5k QPS**。
- ✅ 纯 HTTP 基础峰值约 **19.7k QPS**，说明当前热点查票的主要增量成本在 JWT、Redis 往返、快照反序列化和 JSON。
- ✅ MySQL 回源容量约 **3.4k QPS**；Hikari 从 20 增加到 40 没有稳定收益。
- ✅ 256 并发时整机 CPU 已达 99%，后端约 10.9 核；512 并发吞吐回落且 P99 升至 141ms。
- 🔜 下一轮真实服务器压测必须把压测器放到另一台机器；当前客户端与服务端争抢同一批 32 个逻辑处理器，无法继续准确测高。
- 🔜 在独立压测机可用后，再评估 Tomcat 最大线程、Linux 内核网络参数、JVM GC 和更大 MySQL Buffer Pool。
- ✅ 最新索引版热缓存 128 并发 60 秒实测 **13217.86 QPS / 0 失败 / P99 19.20ms**，同条件比改造前提升约 **14.6%**。
- ✅ cache Redis 全停后，慢查询形成约 **3.5k QPS** 平台；256 并发仍 0 失败，但 P99 约 171ms。
- ✅ cache 故障时 MySQL 约 6.6 核、Hikari 20 连接未耗尽，当前数据规模不会被直接打爆。
- ✅ 1000 车次下 128 并发热点查票 60 秒为 **12445.95 QPS / 0 失败 / P99 22.69ms**。
- ✅ 64 并发综合读写 30 秒完成 95092 次操作，**3161.07 操作/秒 / 0 失败 / P99 123.44ms**。
- ✅ RabbitMQ 异步链路 32 并发提交 200 单全部成功，约 **135 单/秒**，队列无积压。
- ✅ 综合测试前后库存均为 23649，待支付订单为 0，没有发现库存泄漏。
- 🔜 真实大数据量下增加慢查询并发舱壁或限流，防止极端流量把 Tomcat 排队压力完全转给 MySQL。
- 🔜 增加已支付订单长期占用库存、支付流水和退票链路的独立并发测试。

## 六、票价与查询性能

- ✅ 每次下单只查一次连续区间价格，不按段循环查 SQL。
- ✅ 查票 SQL 一次聚合最小余票和总票价。
- ✅ 当前 948 条票价数据规模下，MySQL 范围查询已经足够快。
- ✅ 本地静态索引包含 `trainId + seatType -> segmentPrice[]`。
- ✅ 价格在索引构建时按区间求和，查票时不再重复查价格。
- ✅ 停站和线路方向构建本地只读索引，配置变化时整体失效重建。
- 🧪 用命中率、P95/P99、MySQL CPU 和 Redis 网络延迟判断缓存收益。

## 七、RabbitMQ 与异步下单

- ✅ 保留同步下单，同时提供异步下单用于削峰和回退。
- ✅ 先持久化 `order_request`，再 Redis 预扣、MQ 投递。
- ✅ 消息只带 requestId，完整参数以数据库快照为准。
- ✅ 消费者锁请求行，数据库行锁保证重复消息不会重复建单。
- ✅ 配置主队列、死信 Exchange 和死信队列。
- ✅ 消费失败重试、最终失败标记和 Redis 回补。
- ✅ 投递前崩溃由恢复任务补投；处理卡死由恢复任务终止。
- 🔜 增加死信消息后台查看和人工重放工具。
- 🔜 增加队列积压、消费耗时和重试次数监控告警。
- ❌ 不让 RabbitMQ 承担订单最终状态，也不以消息到达代替数据库提交。

## 八、SQL 与数据访问

- ✅ 选择 MyBatis XML，保留 SQL 可见性，不引入 MyBatis-Plus。
- ✅ 批量场景优先一条 SQL，不为每个对象循环访问数据库。
- ✅ 主键自增使用 `useGeneratedKeys` 回填。
- ✅ 金额用 `BigDecimal`，不用 `double`。
- ✅ 下单人数最多 5 人，批量 IN 查询边界明确。
- 🔜 订单统计可使用专用汇总 SQL，不要让页面加载后再 Java 聚合全表。
- 🔜 数据量继续增大时评估批量写入、分区和归档，而不是先拆表。
- 🧪 每次 SQL 优化都用执行计划和真实数据量验证，避免只凭直觉加缓存。

## 九、安全

- ✅ 密码使用 BCrypt，不存明文。
- ✅ 用户端和管理端 JWT 角色隔离。
- ✅ 用户资源 SQL 同时带 `user_id`，防止越权读取别人的订单或乘车人。
- ✅ 订单详情证件号脱敏返回。
- 🔜 数据库密码和 JWT 密钥移到环境变量。
- 🔜 证件号加密存储，并限制日志输出。
- 🔜 登录限流、验证码、防撞库和主动 token 失效。
- 🔜 管理端敏感操作记录管理员操作日志。
