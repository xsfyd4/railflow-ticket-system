## 五、结果分析

### 1. 单并发 QPS 较低不代表系统能力

一个线程发送下一次请求前必须等待上一次请求结束，因此 QPS 约为：

```text
1000 / 平均延迟
```

延迟约 9ms 时，单并发只有约 111 QPS。

### 2. 16 并发是当前最佳工作点

16 并发时 QPS 已接近平台，P95 仍只有约 10ms。

32 和 64 并发时 QPS 基本保持 2.5k，但请求开始排队：

- 32 并发 P95 从 10.18ms 增加到 22.84ms
- 64 并发 P95 增加到 47.81ms

这说明继续堆并发请求不会增加实际吞吐，只会增加等待时间。

### 3. 线程栈确认了连接池瓶颈

在 64 并发运行期间抓取 Java 线程栈，65 个 HTTP 工作线程的分类结果：

| 状态 | 线程数 |
| --- | ---: |
| 等待 Hikari 数据库连接 | 51 |
| 正在等待 MySQL 网络返回或读取结果 | 10 |
| 其他锁等待 | 3 |
| 其他 | 1 |

等待连接池的线程栈停在：

```text
com.zaxxer.hikari.util.ConcurrentBag.borrow
```

当前 HikariCP 最大连接数配置为 10，因此吞吐达到约 2.5k QPS 后，
大部分请求线程并不是在执行业务代码，而是在排队等待 10 个数据库连接。

同时，单条车次分页 SQL 的 `EXPLAIN ANALYZE` 执行时间约为 1.8ms，
说明数据库不是完全失去响应，而是查询次数、连接占用时间和连接池上限共同形成了排队。

### 4. CPU 并没有被跑满

在 64 并发期间连续采样 4 秒：

| 进程 | 使用核数 | 占整机 32 线程比例 |
| --- | ---: | ---: |
| Java 后端 | 约 8.37 核 | 26.15% |
| MySQL 服务 | 约 3.38 核 | 10.57% |
| 合计 | 约 11.75 核 | 36.72% |

因此整机 CPU 仍有明显余量。当前是请求在 10 个数据库连接上排队，
不是 CPU 完全算不过来。

MySQL `performance_schema` 中三类查票 SQL 的平均执行时间约为：

```text
countTrains：  0.327ms
findTrainIds： 0.346ms
findSeatRows： 0.590ms
```

单次请求的三条 SQL 合计约 1.26ms，但每次 MyBatis 查询都可能发生一次
Hikari 连接的借出与归还。一次 HTTP 请求涉及三次连接调度，会显著放大高并发下的
Hikari 队列竞争。

此外，本次 8080 实例由 IDEA 启动，JVM 参数中包含：

```text
-XX:TieredStopAtLevel=1
```

这限制了 JIT 只使用 C1，适合快速启动和调试，但会降低长期运行时的 Java 吞吐能力。
生产环境或正式压测应使用正常的分层 JIT 参数。

主要限制因素：

1. 单个查票请求需要执行三次 SQL：
   - 统计车次数
   - 分页查车次 id
   - 查席别、余票和价格
2. HikariCP 最大连接数只有 10。
3. 查票 Service 没有只读事务，三次查询没有显式复用同一个连接和事务。
4. 应用和 MySQL 共用本机 CPU、磁盘和内存。
5. `com.ticket=debug` 会输出大量 SQL 参数日志。
6. IDEA 启动参数 `-XX:TieredStopAtLevel=1` 限制 JIT 优化。
7. 每次请求都要经过 JWT 解析和 JSON 序列化。

线程栈已经证明首要排队点是 HikariCP。后续提高连接池可以继续观察瓶颈会转移到
MySQL CPU、应用 CPU 还是数据库查询本身；不能只通过扩大连接池掩盖 SQL 和缓存问题。

### 5. 连接池 10 与 20 的对照测试

为避免 Tomcat、网络和 IDEA 调试 JIT 参数混入，新增两个手动基准：

- `DatabasePoolBenchmarkTest`：只执行与查票相同类型的三条 SQL。
- `HttpPipelineBenchmarkTest`：走完整 Spring MVC、JWT、Controller、Service、
  MyBatis 和 JSON，但不经过真实 Tomcat TCP。

两个测试都使用 64 个并发线程、持续 4 秒、相同数据库和查询参数。

| 场景 | 池大小 10 | 池大小 20 | 变化 |
| --- | ---: | ---: | ---: |
| 数据库访问层 QPS | 9201.52 | 15557.34 | 约 +69% |
| 数据库访问层 P95 | 42.41ms | 20.97ms | 约 -51% |
| Spring MVC QPS | 1716.59 | 3102.65 | 约 +81% |
| Spring MVC P50 | 36.17ms | 17.64ms | 约 -51% |

结果表明连接池从 10 调到 20 确实有效，连接池是当前最直接的可调瓶颈之一。

继续把 Spring MVC 基准的请求线程从 64 增加到 128，连接池保持 20：

| 并发线程 | QPS | P50 | P95 | P99 |
| ---: | ---: | ---: | ---: | ---: |
| 64 | 3102.65 | 17.64ms | 47.64ms | 59.91ms |
| 128 | 2477.24 | 48.94ms | 80.30ms | 109.12ms |

增加过多请求线程反而降低吞吐，说明当前应用的适宜并发量约为 64。
继续增加线程只会加重排队、线程切换和单机 CPU 调度压力。

注意：

- Spring MVC 进程内测试不包含真实 Tomcat TCP 和网络开销。
- 当前已经运行的 8080 实例仍是启动时的 10 连接配置，需要重启才能应用新配置。
- 重启后必须用 `scripts/load_test.py --workers 64` 再测真实 HTTP。

### 6. 只读事务对照：多轮结果与最终选择

曾尝试给 `TicketServiceImpl.search()` 添加：

```java
@Transactional(readOnly = true)
```

目的是一次持有连接完成三次 SQL。

第一次单轮测试噪声较大，因此增加 `ReadTransactionBenchmarkTest`：

- 64 并发、连接池 20
- 每个场景先做 1 秒并发预热
- 无事务和只读事务交替运行 3 轮
- 每轮正式采样 2 秒

| 场景 | 第 1 轮 QPS | 第 2 轮 QPS | 第 3 轮 QPS | 稳定阶段 P95 |
| --- | ---: | ---: | ---: | ---: |
| 无事务 | 3178.36 | 5970.11 | 5897.70 | 约 16.4ms |
| 只读事务 | 4722.21 | 5659.33 | 5425.73 | 约 4.8ms |

预热后无事务吞吐约高 7%，只读事务的中位和尾延迟更低，但事务会让一个请求长期占用
20 个连接中的一个。当前下一步要接 Redis，缓存命中时不应获取数据库连接，因此决定：

- 暂不给 `TicketServiceImpl.search()` 整个入口添加事务。
- Redis 命中路径保持零 MySQL 连接。
- 后续只在缓存未命中的独立数据库回源 Service 中评估短只读事务。

## 九、Redis 查票结果缓存实测

### 实现方式

- 缓存完整分页查票结果，命中时不访问 MySQL。
- Redis 客户端切换为同步 Jedis。
- TTL 默认 10 秒。
- Key 包含全局版本、日期版本、起止站、日期、席别和分页参数。
- 库存变化递增日期版本。
- 车次、停站、票价和车站变化递增全局版本。
- 旧版本缓存不扫描删除，等待 TTL 自动过期。
- Redis 不可用时降级查询 MySQL。

### 基准结果

相同 Spring MVC 进程内测试、64 并发、连接池 20：

| 场景 | QPS | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: |
| 无缓存第 1 次 | 1620.53 | 33.17ms | 86.51ms | 123.66ms |
| 无缓存第 2 次 | 2402.95 | 25.05ms | 40.09ms | 55.48ms |
| Redis 缓存命中，64 并发 | 4901.74 | 11.99ms | 24.41ms | 33.02ms |
| Redis 缓存命中，128 并发 | 5829.12 | 20.32ms | 43.61ms | 59.08ms |

无缓存在不同运行间波动较大，但缓存命中路径明显更高。
缓存功能验证了：

- 第一次查询回源 MySQL 并写入 Redis。
- 相同版本第二次查询直接读取 Redis。
- 手工调整库存提交后，下一次查票读取到新余票。
- 下单、取消和退票提交后，下一次查票读取到新余票。
- Redis 指向不可用端口时，查票仍能通过 MySQL 正常返回。

注意：以上仍是 Spring MVC 进程内基准，不包含真实 Tomcat TCP。
需要重启 8080 后使用 `scripts/load_test.py` 重新测真实 HTTP。

## 十一、2026-10-28：Redis 高可用版本真实 HTTP 极限压测

### 11.1 测试目标

本轮不再使用 Spring MVC 进程内调用，而是从 Windows 宿主机通过真实 TCP 访问
Docker 中运行的 Spring Boot 服务。目标分为三层：

1. `/api/public/ping`：测 Tomcat、Spring MVC 和 JSON 的基础吞吐上限；
2. Redis 热点查票：测 JWT + Replica 读取 + 快照反序列化 + JSON 返回的线上主路径；

### 11.5 MySQL 回源查票

临时在 `8081` 启动关闭查票缓存的实例，每个请求都执行真实的 3 条 MySQL 查询。
Hikari 最大连接数先保持 20：

| 并发 | QPS | P95 | P99 | 失败 |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 1337.90 | 9.86ms | 13.94ms | 0 |
| 16 | 2656.88 | 8.00ms | 10.68ms | 0 |
| 32 | 3308.74 | 13.24ms | 16.05ms | 0 |
| **64** | **3368.84** | **33.48ms** | **42.60ms** | **0** |

把 Hikari 从 20 调到 40 后：

| 并发 | QPS 范围 | P99 范围 | 结论 |
| ---: | ---: | ---: | --- |
| 32 | 2591～3309 | 36.41ms | 波动大，无稳定收益 |
| 64 | 3193～3432 | 32.22～36.77ms | 与池 20 的 3369 QPS 基本同量级 |

64 并发回源期间采样：

- 后端 CPU：约 5.95 核；
- MySQL CPU：约 3.82 核；
- MySQL 数据库连接：60 个，其中 `Threads_running` 约 7；
- Redis CPU：几乎空闲。

结论：

- MySQL 回源查票容量约 **3.4k QPS**。
- 连接池从 20 提升到 40 没有稳定收益，说明限制不在 Hikari 数量。
- 60 个连接中通常只有少数查询线程在运行，主要成本是每条请求的 3 次 SQL、
  MyBatis 映射和应用侧 CPU。

### 11.6 资源瓶颈

128 和 256 并发热点查票期间：

| 资源 | 128 并发 | 256 并发 |
| --- | ---: | ---: |
| 后端 CPU | 约 10.2 核 | 约 10.9 核 |
| Redis Master | 约 96% 单核 | 约 89% 单核 |
| 两个 Replica | 约 67%～72% 单核 | 约 63%～65% 单核 |
| 后端内存 | 约 1.0GB | 约 1.0GB |
| 整机 CPU | 96% | 99% |

当前主要限制：

1. 压测客户端、后端、MySQL 和 Redis 共享同一台电脑的 32 个逻辑处理器；
2. 256 并发时整机 CPU 已经到 99%，继续增加并发只会排队；
3. Redis 三节点各约半核到一核，不是当前首要瓶颈；
4. MySQL 回源时数据库约 3.82 核，但连接并非全部繁忙，SQL 次数和请求链路是主成本；
5. 后端内存约 1GB，远低于 7.62GB Docker 上限，不是内存瓶颈。

### 11.7 最终结论

在这台电脑、同一宿主机同时运行压测端和全部服务的条件下：

| 场景 | 结果 |
| --- | ---: |
| 纯 HTTP 峰值 | **约 19.7k QPS** |
| Redis 热点查票短时峰值 | **约 12.8k QPS** |
| Redis 热点查票 60 秒稳定值 | **约 11.5k QPS** |
| MySQL 回源查票峰值 | **约 3.4k QPS** |

这组数字可以说明当前架构已经明显超过旧 MySQL 版本的约 2.5k QPS，但不能代表
线上服务器容量。要测服务器真正上限，下一轮必须把压测器放到另一台机器，
避免客户端与服务器争抢同一批 32 个 CPU 线程。
