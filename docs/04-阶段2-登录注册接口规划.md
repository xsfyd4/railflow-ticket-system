# 04 · 阶段 2 规划：登录注册

> 阶段 2 要做哪些接口、每个接口干什么、文件放哪、拆成几步做。

---

## 一、这一步的边界和完成标准

**做什么**：用户端注册登录、管理端登录，以及保护接口的 JWT 拦截器。

**只碰两张表**：`sys_user`（用户端账号）、`sys_admin`（管理端账号）。业务表（车次、库存、订单）
这一步一律不动。

**完成的标准**：三件事全做到。

1. 用户能注册，密码加密入库（数据库里看不到明文）
2. 用户能登录，拿到 token
3. 不带 token 或 token 过期时，访问受保护接口被挡回来

---

## 二、要写的接口

一共 6 个。

### 用户端

| 方法 | 路径 | 作用 | 要登录 |
| --- | --- | --- | --- |
| POST | `/api/user/auth/register` | 注册新账号 | 否 |
| POST | `/api/user/auth/login` | 登录，返回 token | 否 |
| GET | `/api/user/auth/me` | 查当前登录人信息 | 是 |
| POST | `/api/user/auth/logout` | 退出登录 | 是 |

### 管理端

| 方法 | 路径 | 作用 | 要登录 |
| --- | --- | --- | --- |
| POST | `/api/admin/auth/login` | 管理员登录，返回 token | 否 |
| GET | `/api/admin/auth/me` | 查当前管理员信息 | 是 |

### 每个接口的入参和出参

**注册** `POST /api/user/auth/register`

```json
// 请求
{ "username": "zhangsan", "password": "123456", "nickname": "张三", "phone": "13800000000" }

// 响应
{ "code": 200, "msg": "注册成功，请登录", "data": null }
```

**登录** `POST /api/user/auth/login`

```json
// 请求
{ "username": "zhangsan", "password": "123456" }

// 响应
{ "code": 200, "msg": "操作成功",
  "data": { "token": "eyJhbGciOi...", "userId": 1, "username": "zhangsan", "nickname": "张三" } }
```

**查当前登录人** `GET /api/user/auth/me`

```json
// 请求头
Authorization: Bearer eyJhbGciOi...

// 响应（注意：绝不能包含 password 字段）
{ "code": 200, "msg": "操作成功",
  "data": { "id": 1, "username": "zhangsan", "nickname": "张三", "phone": "138****0000" } }
```

`/api/admin/auth/*` 结构完全一样，只是换成查 `sys_admin` 表、发的 token 里 role 是 `ADMIN`。

### 关于 logout 的实话

JWT 是无状态的：token 一旦签发，服务端不存它，也就「删不掉」。
所以真正的退出其实是**前端把浏览器里存的 token 丢掉**，服务端这个接口只是形式上的。

要在服务端真正让某个 token 立刻失效，得引入「黑名单」机制（通常放 Redis）——
那属于阶段 8 的优化范畴。现在这个接口直接返回成功即可，但你要知道它为什么是空的。

## 四、几个关键设计

### 1. JWT 里放什么

```json
{
  "sub": "1",          // 用户 id
  "role": "USER",      // 角色：USER 或 ADMIN
  "name": "zhangsan",  // 用户名
  "iat": 1760000000,   // 签发时间
  "exp": 1760604800    // 过期时间（7 天后）
}
```

**绝对不能放**：密码、身份证号、手机号这类敏感信息。

原因：JWT 的内容只是 Base64 编码，**不是加密**。任何人拿到 token，粘到
[jwt.io](https://jwt.io) 就能看到里面写了什么。它只能证明「这段内容没被改过」，不能保密。

### 2. 拦截器怎么工作

```text
请求进来
  ▼
从请求头取 Authorization: Bearer xxx
  ▼
没带 token？          → 返回 401「未登录」
  ▼
解析失败/已过期？     → 返回 401「登录已过期」
  ▼
token 里的 role 不对？ → 返回 403「没有权限」
  ▼
把 userId / username 放进 LoginUserContext
  ▼
放行，进入 Controller
  ▼
finally 里清空 LoginUserContext
```

**为什么要有 `LoginUserContext`**：Controller 和 Service 里经常需要知道「现在是谁在操作」，
比如下单要记 userId。如果每层都加一个参数一路传下去，代码会很难看。
用 `ThreadLocal` 存一份，谁需要谁去取。

**为什么一定要在 finally 里 clear()**：Tomcat 的线程是复用的。
不清干净的后果很严重——A 用户的请求用完这个线程，B 用户的请求又用了同一个线程，
结果 B 读到了 A 的登录信息。这是很典型的安全事故。

### 3. WebMvcConfig 里怎么注册

```java
registry.addInterceptor(jwtInterceptor)
        .addPathPatterns("/api/user/**")
        .excludePathPatterns("/api/user/auth/register",
                             "/api/user/auth/login");

registry.addInterceptor(adminJwtInterceptor)
        .addPathPatterns("/api/admin/**")
        .excludePathPatterns("/api/admin/auth/login");
```

注意：**管理端拦截器只认 role=ADMIN 的 token**。
就算普通用户登录拿到了 token，拿去调 `/api/admin/**` 也会被 403 挡掉。
这是最基础也最重要的一道安全线。

### 4. 密码怎么处理

```java
// 注册：转成密文再入库
user.setPassword(passwordEncoder.encode(dto.getPassword()));

// 登录：不是解密比对，而是让 BCrypt 重新加密输入的密码再和库里比对
if (!passwordEncoder.matches(dto.getPassword(), user.getPassword())) {
    throw new BizException(ResultCode.LOGIN_FAILED);
}
```

BCrypt 是**单向**的，加密后无法还原。所以登录时不能「解密」，只能用 `matches()` 比对。

还有一点：登录失败时，提示语统一用「用户名或密码错误」，**不要**区分成
「用户名不存在」和「密码错误」——那等于告诉攻击者哪些用户名是有效的。

## 五、拆成 4 小步做

| 步骤 | 做什么 | 做完能验证什么 |
| --- | --- | --- |
| 2-2 | 引 `validation` 依赖、写 `SysUser` 实体和 Mapper、确定 ORM 用哪套 | 能按用户名查到一条用户记录 |
| 2-3 | 写注册接口（BCrypt 加密） | 数据库里能看到新用户，且密码是 `$2a$10$...` 这样的密文 |
| 2-4 | 写登录接口，签发 JWT | 用 Postman / IDEA HTTP Client 请求能拿到 token |
| 2-5 | 写拦截器 + `me` 接口 + 管理端登录 | 不带 token 被挡 401；带上能拿到自己的信息；用户 token 调管理端被挡 403 |

每小步做完都能独立验证，不要一次写完再一起调。

## 六、这一步最容易踩的坑

| 坑 | 后果 | 怎么避免 |
| --- | --- | --- |
| 密码明文入库 | 数据库泄露 = 全站账号沦陷 | 注册时就用 BCrypt，`matches()` 比对 |
| 接口返回了 password 字段 | 前端 F12 就能看到密码哈希 | 用 `UserVO`，不要直接返回 `SysUser` 实体 |
| JWT 里放了敏感信息 | 任何人解码就能看到 | token 里只放 id、role、name |
| ThreadLocal 忘了 clear | 用户之间串数据，严重安全事故 | 拦截器 `finally` 里 `remove()` |
| 拦截器把登录接口也拦了 | 永远登录不上（死锁） | `excludePathPatterns` 排除登录注册 |
| token 没过期时间 | 泄露后永久有效 | `exp` 设 7 天 |
| 登录失败提示太具体 | 泄露哪些用户名存在 | 统一提示「用户名或密码错误」 |
| CORS 和拦截器顺序搞错 | 前端发 OPTIONS 预检请求被 401 挡住 | 拦截器里放行 `OPTIONS` 请求 |

最后一条特别容易忘：浏览器发跨域请求前会先发一个 `OPTIONS` 预检请求，
它**不带 Authorization 头**，如果被拦截器拦下返回 401，前端就会报跨域错误，
而且错误信息完全指不到真正的原因。
