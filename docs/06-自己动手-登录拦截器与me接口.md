## 一、这次要完成什么

**登录拦截器** + **「查当前登录人」接口**。

做完之后，这套闭环就通了：

```text
注册 → 登录拿 token → 带着 token 访问受保护接口 → 通过
                    → 不带 token 访问 → 被挡回来 401
                    → 带一个被篡改的 token → 被挡回来 401
```

这是整个项目第一个真正完整的机制。后面所有需要登录的接口（下单、查订单……）
都靠它保护，所以必须吃透。

### 完成标准

1. 不带 token 访问 `/api/user/auth/me` → 返回 401
2. 带正确的 token 访问 → 返回当前登录人的信息，**且没有 password 字段**
3. 把 token 末尾改几个字符再访问 → 返回 401
4. 不带 token 访问 `/api/user/auth/login` → 正常返回（说明排除规则生效了）

## 二、要新建的 3 个类

### 1. `security/LoginUser.java`

**职责**：装「当前登录人」的数据。不是给前端看的，是给后端内部用的。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | Long | 用户主键，从 token 的 sub 里取 |
| username | String | 用户名，从 token 的 name 里取 |
| role | String | 角色，USER 或 ADMIN，从 token 的 role 里取 |

普通 Java 类，加 getter/setter 即可。可以再写一个构造器方便 new。

> 为什么不让它直接复用 `UserVO`？因为职责不同：
> `LoginUser` 是「token 里有什么」，`UserVO` 是「返回给前端看什么」。
> 现在字段碰巧差不多，但以后 token 里会加东西（比如登录设备），
> 前端要的也会变，混用会越来越别扭。

### 2. `security/LoginUserContext.java`

**职责**：在「一个请求的处理过程中」共享当前登录人。

需要三个静态方法：

| 方法 | 作用 |
| --- | --- |
| `static void set(LoginUser user)` | 存进去 |
| `static LoginUser get()` | 取出来（Controller/Service 用） |
| `static void clear()` | 清掉（**极其重要**） |

内部用一个 `ThreadLocal<LoginUser>`。

> 为什么要用它？因为 Controller 和 Service 经常需要知道「现在是谁在操作」。
> 如果靠参数一层层传（`method(dto, userId)`），代码会很难看。
> 用 ThreadLocal 存一份，谁需要谁去取。
>
> **为什么必须 clear？** Tomcat 的线程是复用的：A 用户的请求用完这个线程，
> B 用户的请求又用同一个线程。不清干净，B 就会读到 A 的登录信息。
> 这是典型的安全事故，不是「最好清一下」的建议，是必须。

### 3. `security/JwtInterceptor.java`

**职责**：拦截请求，验 token，把登录人放进 `LoginUserContext`。

实现 `org.springframework.web.servlet.HandlerInterceptor` 接口，
重写两个方法：

```java
boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                     Object handler, Exception ex)
```

`preHandle` 里要做的判断，按顺序：

| 步骤 | 判断 | 不通过怎么办 |
| --- | --- | --- |
| 1 | 是 `OPTIONS` 请求吗？ | **直接放行**（见下面的坑 3） |
| 2 | 取 `Authorization` 请求头 | 为空 → 401 |
| 3 | 是以 `Bearer ` 开头吗？ | 不是 → 401 |
| 4 | 截掉 `Bearer ` 前缀拿到 token | |
| 5 | 调 `jwtUtil.parse(token)` | 抛 `JwtException` → 401 |
| 6 | 从 claims 取 `sub`、`name`、`role` | |
| 7 | `LoginUserContext.set(...)` | |
| 8 | 返回 `true` 放行 | |

`afterCompletion` 里只有一件事：`LoginUserContext.clear()`。

### 拦截器注册规则

```java
registry.addInterceptor(jwtInterceptor)
        .addPathPatterns("/api/user/**")                 // 只管用户端
        .excludePathPatterns("/api/user/auth/register",  // 注册要放行
                             "/api/user/auth/login");    // 登录要放行
```

**只拦 `/api/user/**`，别去动 `/api/public/**` 和 `/api/admin/**`**
（管理端下一步单独做一套）。

### `getCurrentUser()` 要做什么

```text
1. 从 LoginUserContext 取出当前登录人
2. 取不到 → 抛 BizException(UNAUTHORIZED)
3. 用 id 去数据库查完整的用户（不是直接用 token 里的信息）
4. 转成 UserVO 返回
```

第 3 步是关键：**token 里的信息是签发那一刻的快照**，用户可能已经改过昵称了。
所以真正的 user 信息要现查数据库。

## 四、新接口

### `GET /api/user/auth/me`

```text
请求头：Authorization: Bearer eyJhbGciOi...

响应：
{ "code": 200, "msg": "操作成功",
  "data": { "id": 1, "username": "zhangsan", "nickname": "张三", "phone": "138****0000" } }
```

不带 token 时：

```text
{ "code": 401, "msg": "未登录或登录已过期", "data": null }
```

## 五、五个必踩的坑（先看，能省你两小时）

### 坑 1：`preHandle` 返回 false 不会自动返回 JSON

在拦截器里 `return false` 只是「不再往下走了」，**响应体是空的**，
前端只会看到一个空的 200 响应。

你必须自己往 response 里写内容。用到的 API：

- `response.setStatus(...)`
- `response.setContentType("application/json;charset=UTF-8")`
- `response.getWriter().write(字符串)`

麻烦的是「把 `R` 对象转成 JSON 字符串」——拦截器里没有 Spring 的转换器帮忙。
提示：可以注入 Spring Boot 自带的 `ObjectMapper`（Jackson 的类），
用它的 `writeValueAsString(obj)` 方法。

> 想想为什么要设 `charset=UTF-8`？不设的话中文提示会变成乱码。

### 坑 2：ThreadLocal 忘了 clear

必须在 `afterCompletion` 里清。而且要注意：
如果 `preHandle` 在中间就 `return false` 了，`afterCompletion` **还会被执行**吗？
（答案：会，但只对「已经返回 true 的那些拦截器」。所以你自己要理清楚在哪儿清最稳妥。
最保险的做法是：`preHandle` 里只要写入了 ThreadLocal，就一定保证有对应的清理。）

### 坑 3：`OPTIONS` 预检请求不带 token

浏览器发跨域请求前，会先发一个 `OPTIONS` 请求探路，**它不带 `Authorization` 头**。
如果被拦截器挡下返回 401，前端会报「跨域错误」——错误信息完全指不到真正的原因，
能查一整天。

所以第一步就要判断：是 `OPTIONS` 就放行。

### 坑 4：登录注册接口没排除

如果忘了 `excludePathPatterns`，会出现「想登录必须先登录」的死锁。
而且提示是 401「未登录」，你可能会以为是 token 的问题，绕很久。

### 坑 5：token 前缀的处理

请求头格式是 `Bearer eyJhbGciOi...`，中间有一个空格。
截取时别把空格也当 token 的一部分，否则解析必然失败。
提示：`substring("Bearer ".length())`。
